Deployment Guide

Learn how to deploy your TeapotApps backend application across diverse architectures: standalone Node.js servers, Docker containers, PaaS platforms, and serverless environments like Vercel.

1. Architecture Overview

TeapotApps is designed to be deployment-agnostic. It runs seamlessly as a persistent HTTP service or within ephemeral serverless function runtimes:

Deployment Mode Recommended Platforms Configuration Required Best For
Standalone Process VPS (PM2 / Systemd), Docker, Railway, Render, Fly.io None (Zero-config, native npm start) APIs with continuous DB pooling, long-lived websockets, and background cron jobs.
Serverless Function Vercel vercel.json with includeFiles Event-driven REST APIs, JAMstack backends, and serverless microservices.

2. Standalone Server Deployment (VPS & Docker)

In standalone deployments, TeapotApps executes as a persistent Node.js process using native ESM. The full file system remains intact on the server disk.

Production Command

# Start server in production mode:
npm start

# Or with explicit environment variables:
NODE_ENV=production node index.js

Using Process Manager (PM2)

For Ubuntu / Debian servers or cloud instances (AWS EC2, DigitalOcean Droplet, Linode), use PM2 to ensure automatic restarts and cluster scaling:

# Install PM2 globally:
npm install -g pm2

# Start TeapotApps service:
pm2 start index.js --name "teapotapps-backend"

# Save process list for system reboot:
pm2 save
pm2 startup

Docker Deployment

You can package TeapotApps into a lightweight Alpine container:

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 3010
CMD ["npm", "start"]

3. Serverless Deployment on Vercel

Vercel compiles Node.js projects into ephemeral AWS Lambda functions located in isolated container directories (such as /var/task).

Scaffolding with CLI

When creating a new project, select the Vercel Ready option in the feature checklist:

npm create teapotapps@latest my-app

The CLI automatically configures an optimal vercel.json file targeting your application.

Manual Configuration (`vercel.json`)

If you created a project without the Vercel option or are migrating an existing backend, create vercel.json in your project root:

{
  "version": 2,
  "builds": [
    {
      "src": "index.js",
      "use": "@vercel/node",
      "config": {
        "includeFiles": [
          "src/views/**",
          "views/**"
        ]
      }
    }
  ],
  "routes": [
    {
      "src": "/(.*)",
      "dest": "index.js"
    }
  ]
}
Why `includeFiles` is Critical on Vercel:
Vercel traces dependencies at build time using static analysis via @vercel/nft. Because TeapotApps view rendering (render(res, 'ViewName')) loads view components dynamically at runtime, the static tracer cannot predict file usage. Specifying includeFiles: ["src/views/**"] forces Vercel to package your SSR view templates into the serverless bundle, preventing 500 Cannot find module errors.

4. Database Connection Pooling in Serverless

In serverless environments, each incoming request may trigger a new Lambda container. Direct database connections can quickly saturate connection limits (such as PostgreSQL max_connections).

For serverless deployment on Vercel with databases, use managed cloud database providers featuring built-in connection poolers:

  • Supabase: Use Transaction mode (port 6543) via PgBouncer.
  • Neon PostgreSQL: Use the pooled connection string (-pooler subdomain).
  • PlanetScale: Serverless MySQL architecture with automated connection offloading.

5. Environment Variables

Ensure that all required variables are configured in your hosting platform (Vercel Project Settings or Server .env):

APP_NAME=TeapotApps
APP_PORT=3010
APP_DEBUG=false
APP_KEY=your_random_32_character_secret_key
APP_ACCESS_TOKEN_SECRET=your_jwt_signing_token_secret
APP_DB_CONNECTION=postgres
APP_DB_HOST=aws-0-us-west-1.pooler.supabase.com
APP_DB_PORT=6543
APP_DB_DATABASE=postgres
APP_DB_USERNAME=postgres.your_project_ref
APP_DB_PASSWORD=your_secure_db_password
Production Tip: Always set APP_DEBUG=false in production to suppress detailed internal stack traces from client JSON responses.
